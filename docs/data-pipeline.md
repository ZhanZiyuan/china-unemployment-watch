# Collection, quality and publication

Run `pnpm fetch-data` in a dedicated checkout. It discovers releases within a four-month publication lookback, validates both required sources, merges by source, series and period start, and stages a complete data snapshot. The first collection and `pnpm fetch-data --backfill` attempt 2023-01-01 through 2026-11-17 inclusive. Manual backfill inserts missing periods into the existing dataset. The incremental publisher applies revisions only in the lookback window. Run `pnpm fetch-data --from-archive` to regenerate JSON offline using the archived evidence and current algorithm. That command has no network side effects and leaves collection health untouched.

- `data/raw/` contains gzip-compressed official release response bodies. The filenames address the SHA-256 of the original body.
- `data/metadata/` contains URL, HTTP status, timestamp, and release catalog metadata. `initial-backfill.json` records the initial live batch before replay.
- `data/processed/observations.json` contains stable records with one observation per series and native period.
- `data/revisions/observations.json` is written when a snapshot changes under the live collection path. Every replacement retains the previous and new observation with both raw hashes. Each revision ID hashes the prior observation and the newly extracted observation. Git commit history retains past snapshots and publication files.
- `public/data/latest.json` contains the validated snapshot and coverage. The manifest gives its algorithm and content versions and the exact file checksum. The three JSON Schemas describe interchange structure. `pnpm validate-data` also enforces cross-field, raw replay, and checksum invariants.
- `public/data/collection-status.json` records the last attempted collection, including failure. The actual UTC and Shanghai times come from the runner's clock. The timestamp on a retained observation comes from the response that supplied its value. The dataset version records the material snapshot and coverage. A same-month no-change refresh can update collection status while preserving the data version.

The quality gate checks finite values, source-specific ranges and units, period shape and bounds, timestamp order, uniqueness, required-source availability, freshness and zero variance. It rehashes and reparses every referenced archived body and both sides of each revision. A large consecutive month change is flagged for review. True source-reported values remain visible. Historical gaps are recorded separately. Missing records and fetch errors produce no numeric observation.

GitHub runs a single writer on `17 3 * * *` UTC, on every `main` push including PR merges, and via manual dispatch on `main`. A shared concurrency group serializes data writes. The workflow checks out the current main head, stages allowlisted paths, and uses a non-force push. A conflicting human push causes a safe refusal from Git. The repository token suppresses workflow recursion and the job has a bot guard. A source or data-quality failure retains the last validated dataset and can commit collection status alone. Logs are attached to the workflow run, and a failed run uses GitHub Actions failure notifications.

Manual dispatch on `develop` runs the same live collection and quality checks on a GitHub-hosted runner. This check uploads the collection report without pushing files or deploying to production. The collector reads the release archive in page order until the requested window is covered. It retries transient transport failures on the affected page and records the page URL and nested error if it still fails.

Vercel's production branch must be `main`. The updater can fire a main-branch `VERCEL_DEPLOY_HOOK` secret if the Git integration needs it for bot commits. Set the GitHub variable `PRODUCTION_URL` if the production URL changes. The workflow waits for Vercel to serve the exact manifest, dataset checksum and collection-status bytes. GitHub branch rules must permit the selected data writer's allowlisted commit. Deployment access, the live scheduled event, overlapping live triggers and production checks await the owner's merge.

NBS returned valid release bodies during initial acquisition and also returned intermittently blocked pages with HTTP 200. The collector uses alternate official publication routes and refuses access-challenge pages. Continued release access from GitHub-hosted runners remains a deployment check.
